# toride-swap-decision

Answer to the question: why not replace superai's own install stack with toride?

## Verdict

Partial adoption. superai takes toride-apps' backend execution layer for six method kinds, npm, cargo, pipx, uv, Homebrew formula, and Homebrew cask, and runs it through a superai-owned bridge that forces superai's security posture onto every child process. Everything else stays native: the install catalog, the receipts ledger, update compatibility gating, detection, drift discovery, process.rs, error.rs, and the mise execution path. The Apps facade, its record store, the registry adapters, the standalone detector, and the mise and direct backends are not adopted.

A full swap is ruled out by the matrix, not by doubt about the verbs. Two requirements conflict with toride's semantics rather than merely lagging them, and one is missing outright:

- Receipts. toride records an install even when its own post-install probe cannot confirm the binary, as a warning string on a success value (crates/toride-apps/src/apps.rs:774-805; warning text at :781-788, record insert at :796-799). An unparseable manifest is quarantined aside so the store loads empty and work continues (crates/toride-apps/src/store.rs:107-129). superai fails closed on both counts: a receipt persists only after verify_install proves a new binary (crates/superai-core/src/install_execute.rs:760-763), and an unparseable receipt file is a typed error (install_execute.rs:300-304, :351-355). Receipts are the ownership proof uninstall leans on. Adopting toride's records would assert control over installs nobody verified.
- Sync core. async-trait is a non-optional toride-apps dependency (crates/toride-apps/Cargo.toml:32) and the primary facade is async. superai's rule is plain std threads with no tokio anywhere (crates/superai-core/Cargo.toml:25). I re-ran the checks this session: zero `tokio` entries in superai's Cargo.lock and zero tokio, async fn, or .await hits across superai's crates.
- Drift discovery does not exist in toride in any form. There is no discovery module, and adopt() claims an install on caller-asserted provenance plus a single presence probe (apps.rs:1068-1098). superai's discovery.rs is a 3124-line bounded read-only scanner. There is nothing to swap with.

Why adopt anything at all: the six backends execute real package managers through one injectable seam (Backend::install_sync, uninstall_sync, update_sync at crates/toride-apps/src/backend.rs:497-513, over CommandRunner::new(Arc<dyn Runner>) at crates/toride-apps/src/runner.rs:79-88), their argv comes from a pure planner with tests pinning it verbatim, and superai currently duplicates that argv maintenance by hand in build_command_preview (install_plan.rs:682-745) with two bugs toride does not have. Covering six managers twice is maintenance superai should not carry.

## The belief, checked

The belief: toride gained a lot of install and uninstall functionality for CLI apps and GUIs, with cargo, uv, and npm support.

True for the verbs. I read the backend code this session.

- npm: install, uninstall, and update each run the real npm through run_checked over the runner seam (crates/toride-apps/src/backends/npm.rs:77-89, :91-102, :104-113). The argv is `npm install -g pkg[@version]`, built by the pure planner (crates/toride-apps/src/plan.rs:559-565, npm_spec at plan.rs:67-74, the package@version spelling at plan.rs:1194-1199), with a test pinning the argv verbatim (npm.rs:422-445).
- cargo: `cargo install [--version v]`, `cargo uninstall`, `cargo install --force` for updates (crates/toride-apps/src/backends/cargo.rs:79-91, :93-101, :106-114; argv at plan.rs:566-570 and cargo_install_argv at plan.rs:76-87; tests at cargo.rs:536-553).
- uv: `uv tool install pkg[==ver]`, `uv tool uninstall`, `uv tool upgrade` (crates/toride-apps/src/backends/uv.rs:75-87, :89-97, :102-110; argv at plan.rs:574-576, uv_install_argv at plan.rs:89-94).
- pipx: `pipx install`, `pipx uninstall`, `pipx upgrade` (crates/toride-apps/src/backends/pipx.rs:76-88, :90-98, :103-110). A requested version is refused at plan time (plan.rs:1413-1423).
- GUIs: Homebrew cask shares the formula backend (crates/toride-apps/src/backends/homebrew.rs:440-462 install, :464-475 uninstall, :477-486 update) with `--cask` and `--zap` argv from the planner (plan.rs:506-531); flatpak installs with `--or-update --noninteractive` and uninstalls and updates with `--noninteractive` (crates/toride-apps/src/backends/flatpak.rs:492-547, specs at flatpak.rs:705-741). GUI coverage is exactly these two. toride's detector has no .app bundle source.
- Also executing: mise behind its feature gate (crates/toride-apps/src/backends/mise.rs:74-109; the gate at toride-apps Cargo.toml:25-28), apt, dnf, pacman, and apk through scriptable query programs with assume-yes flags and no auto-sudo (crates/toride-apps/src/backends/distro.rs:579-623, plan.rs:230-256), and sha-verified direct downloads behind the `direct` feature (crates/toride-apps/src/backends/direct.rs:114-159 over crates/toride-installer/src/installer.rs:287-348).

Two limits the belief glosses over. First, version selection is uneven. npm can pin @version and cargo and uv carry versions on install, but pipx and all four distro managers refuse a version at plan time (plan.rs:1413-1423, :1317-1326), and no update verb anywhere accepts a target version: the facade refuses with UpdateTargetNotPinnable (apps.rs:1006-1011) and no backend overrides the trait's default pin refusal (backend.rs:464-471). Second, and this is the heart of the answer: executing a command is the smallest part of superai's install stack. The rest is deciding what may run, proving what landed, and proving what superai owns. On those, the matrix.

Sizes follow the blueprint as verified against both codebases this run.

| Build | Size | What it is |
|---|---|---|

What dies in superai: build_command_preview and its per-kind arms (install_plan.rs:682-745), executable_for_method (install_execute.rs:362-372), the update and uninstall fallback preview constructors (install_execute.rs:974-999, :1450-1472), the three dispatch sites (install_execute.rs:733-738, :1167-1172, :1564-1569), and the catalog's update and uninstall command fields (install_catalog.rs:289-294, validation at :351-356, plus the asset edit; disk catalogs stay load-compatible because parsing ignores unknown fields, install_catalog.rs:439-444).

One correction to the blueprint as it came to me: run_structured_command and run_token_command (install_execute.rs:109-160) are not the install-path executor. Their only non-test caller is each other. The swap replaces the three run_command dispatch sites, which is why those are listed above instead.

What survives: the catalog and its validation; the receipts ledger; verify_install and the smoke probes; update compatibility gating and revalidation; the uninstall preflight and guards; pin_exact_binary; detect.rs; discovery.rs; all version availability probing (toride has no availability surface at all); process.rs, which still serves the daemon, activation, wrapper, lifecycle, plugin, and failure paths plus the mise arm and the probes; error.rs and RedactedString; the mise execution path, since toride's mise backend drags tokio through toride-runner's tokio-runner feature (toride-apps Cargo.toml:28); and the typed External and Direct refusals.

Order of work: bridge and deps first with zero behavior change, then the adapter with mapping tests only, then install, then uninstall, then update, then delete the dead arms and run the full gates (cargo fmt, clippy with -D warnings, the workspace tests, and the tokio greps over source and Cargo.lock). The facade decision is deferred on purpose.

## Conditions

1. The bridge lands before any backend call. No superai child runs under toride-apps' spec defaults; they are permissive today (Allow argv, OsSearch, opt-in cap, no clear_env, redact off, with zero opts-in per my grep this session).
2. The maintainer rules on the sync rule's reading: workspace source stays grep-clean of tokio, async fn, and .await, and Cargo.lock stays tokio-free (default features only; mise, direct, and registry-http never enabled), accepting async-trait as a transitive in the lockfile. If the rule is read as lockfile-clean too, this adoption is off and the answer becomes port-only.
3. All three toride crates stay pinned =0.1.0, and every bump review re-runs argv-diff tests over the six kinds' previews. The crates are at 0.1.0, published 2026-10-08, under roughly 30 downloads each per the crates.io check this session's auditors ran earlier today; this sandbox blocks network, so I did not re-check.
4. zap stays false forever. Cask zap deletes associated files, and the ownership rule forbids touching collateral.
5. goal.md:68 is rewritten in the same change that adds the dependencies.

## Risks

- A 0.x single-maintainer dependency can ship breaking changes inside 0.x. The pin plus argv-diff tests bound the blast radius. The local checkout and the published tarballs were not diffed, so the implementing change must build against the fetched crate, not the local path.
- Split truth. With argv from toride and version truth from superai, a toride change to an upgrade verb lands silently in superai previews. The argv-diff tests are the guard.
- User-visible behavior changes: versioned pipx and uv installs refuse instead of passing pkg@version through; cask previews gain --cask, fixing today's plain `brew install name` (install_plan.rs:718-721), which looks up the formula rather than the cask; toride backends add read-only status probes around installs, routed through the bridge.
- superai's own gaps, untouched by this adoption and needing separate fixes: two spawn paths sit outside process.rs (adapters/mod.rs:261 spawns via std::process::Command with silently truncated output at :190-217; daemon.rs:759 and :761 spawn without a timeout), CommandTokens::validate checks fewer metachars than SHELL_METACHARS (install_catalog.rs:95-108), and update gating does not block when availability is unknown (install_execute.rs:1051-1053). The bridge covers only children routed through it.
- Windows parity was not verified; everything in this decision ran on this Linux host.
