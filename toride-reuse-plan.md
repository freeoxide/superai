# toride reuse plan

This report compares superai's crates against toride's to decide which components superai could replace with a toride piece, where it should copy a design instead, and where its own code is the better fit. The repos are /home/axent/fo/superai and /home/axent/fo/toride. Written 2026-10-08. Each section records its own crates.io publish checks from that day.

## TL;DR

The pattern holds in all four areas: superai keeps its own code, and what toride offers today is designs worth copying, not crates worth depending on.

Filesystem layer: KEEP across the board, with one PORT. The port is the permission audit, two small unix checks, because nothing in superai today flags a world-readable secret-bearing config.

Process execution: KEEP, with three PORTs: in-capture output limiting, value-level secret scrubbing, and a Runner test seam. ADOPT is deferred rather than rejected; it unblocks when toride-runner shows a release history or grows runner-level policy defaults.

Install, uninstall, and detection: KEEP the components, and a stack swap is not today. What would change that: a RecordStore bridge over superai's receipts, runner-seam env policy defaults, an External-style typed handoff, update target pinning, and a release history behind the crates.

Update, upgrade, and migration: KEEP, with one PORT: the update outcome shape, UpToDate and Updated with from and to and Preview, in place of a raw ProcessOutput.

The comparison also surfaced two superai bugs. Both are worth fixing whatever superai decides about toride:

- build_command_preview renders a requested version in npm @-syntax for every manager, so cargo, pipx, and uv receive an operand their managers will not resolve (crates/superai-core/src/install_plan.rs:687-694, arms at 706-743). Latent today, because installs run version-less.
- When the availability probe fails, the update plan is not blocked, because blocked requires a known available version (crates/superai-core/src/install_execute.rs:1051-1053), and the post-update version check is skipped for the same reason (crates/superai-core/src/install_execute.rs:1203-1204). An update whose version cannot be probed runs ungated and unverified in one pass.

## Build order

1. Fix the two bugs above. They are internal to superai and rank ahead of anything toride-related, and the operand fix is the same work as the install section's native-version-spelling port.
2. Take the cheap ports, smallest first: the permission audit (roughly fifteen lines, unix-gated, no new dependency), the value-level secret scrub, the Runner seam with UpdateCommandRunner folded in, in-capture output limiting, the detection absorb-merge, adopt as a receipt-writing claim, the update outcome shape, and the elevation and suppression guards for the day a distro method enters the catalog. minimum_release_age waits until superai grows mise invocation options.
3. Revisit the deferred adoptions when their unblocks arrive: toride-runner after a release history or runner-level policy defaults, toride-installer if tokio ever becomes acceptable in superai-core (GPUI makes that unlikely), and the full toride-apps stack once the swap list at the end of the install section is worked through.

### Atomic write

Both sides do the same core: create a temp in the target's directory, write, fsync the temp, rename, fsync the parent. toride does this in `atomic_write_bytes_with_mode` (toride-fs/src/atomic.rs:177-219), creating the temp with the final mode up front so the inode is never visible with looser bits (toride-fs/src/atomic.rs:186-189). superai does it in `atomic_write_expecting` (crates/superai-config/src/atomic.rs:234-366) with an O_EXCL temp whose handle stays open until the bytes are durable, so a pre-planted symlink at the temp name cannot redirect the write (crates/superai-config/src/atomic.rs:258-277).

The differences are in what happens around that core, and they all favor superai:

Durability of the parent fsync. toride treats the directory sync as optional and swallows every error with a trace (toride-fs/src/atomic.rs:80-104). superai surfaces parent-sync failures and tolerates only the error kinds Windows actually produces: Unsupported, PermissionDenied, NotFound (crates/superai-config/src/atomic.rs:147-165). Silence here means a crash can lose the rename with no diagnostic, which sits badly with superai's no-swallowed-Results rule.

Mode preservation. superai derives the replacement's mode from the target when it exists, lands 0o600 for new files, and applies it through the open fd so a name swap cannot redirect the chmod onto a foreign file (crates/superai-config/src/atomic.rs:67-99). toride always lands 0o600 for the plain entry points (toride-fs/src/atomic.rs:32, toride-fs/src/atomic.rs:69-73). A harness config at 0644 that some service reads as another user would silently tighten to 0600 on every edit. Worse, the `atomic_write_with_perms` safety net chmods by path after the rename, and on chmod failure it removes the just-replaced file (toride-fs/src/atomic.rs:133-137). That is a race window where the chmod can land on a swapped-in foreign file, and a failure mode that deletes the config instead of leaving it with a wrong mode. superai removes only its own temp when mode application fails (crates/superai-config/src/atomic.rs:308-311).

Concurrent-modification gating. superai checks a required prior state before creating the temp and rechecks the digest immediately before the rename, aborting untouched on any foreign change (crates/superai-config/src/atomic.rs:190-226 and crates/superai-config/src/atomic.rs:316-327). toride has nothing comparable; its write is last-writer-wins and will clobber a concurrent edit without a signal.

Verification and platform edges. superai reads the file back after the rename and compares bytes (crates/superai-config/src/atomic.rs:354-363), clears the Windows readonly attribute before replacing, and retries a denied rename with growing backoff (crates/superai-config/src/atomic.rs:330-349). toride has neither step; a readonly target on Windows fails the persist outright.

Verdict: KEEP. Nothing in toride-fs/src/atomic.rs is ahead, and the chmod-by-path rollback is the one piece I would not copy under any circumstances.

### Locking

toride-fs offers `with_lock` and `with_lock_path`: open the file, take an fd-lock write guard, run a closure (toride-fs/src/lock.rs:30-51 and toride-fs/src/lock.rs:63-84). superai has no fd-lock dependency anywhere (verified by grep across crates/).

Does superai need one? Its digest gating already catches concurrent writers, including foreign editors that would never take a superai lock; the failure is a typed ConcurrentModification instead of a lost write. A lock would only serialize two superai processes, and toride's implementation would do it badly for this use. The lock is taken on the config file itself, and fd locks bind to the inode. superai replaces files by rename, so the moment the rename lands, the locked inode no longer carries the path and the next process to lock the path locks the new inode. Mutual exclusion silently ends exactly when it matters. The open also creates the file when missing and follows symlinks (toride-fs/src/lock.rs:34-39), so locking a config that does not exist materializes an empty file.

Verdict: KEEP. If process serialization ever becomes a requirement, port the concept with a separate never-renamed .lock file, not this closure over the target itself.

### Permission audits

This is the one genuine gap. toride-fs has `check_not_world_writable` (refuses mode bit 0o002, toride-fs/src/permissions.rs:49-59) and `check_owner_is_root` (toride-fs/src/permissions.rs:70-73), both unix-only. superai has no mode audit; `check_ownership` in executor.rs governs config keys, not file bits (crates/superai-config/src/executor.rs:155-160). superai preserves a target's existing mode across its atomic replace (crates/superai-config/src/atomic.rs:73-81), which is the right default, but the flip side is that a world-readable `.env` full of API keys stays world-readable through every superai edit and nothing ever says so. The snapshot already records permission bits (crates/superai-config/src/snapshot.rs:58-59), so the audit has its data.

Verdict: PORT. Reimplement the two checks, roughly fifteen lines, unix-gated, and warn (or refuse, for `.env`-shaped files) when a secret-bearing config is readable by others. Taking the dependency for this would add tempfile, fd-lock, dirs, and tracing (toride-fs Cargo.toml dependencies) for two boolean functions.

### Path expansion vs safe_paths

The two crates answer the same question oppositely. toride expands: `~` to home, `$HOME` interpolated from the environment (toride-fs/src/expand.rs:29-46 and toride-fs/src/expand.rs:63-75). superai refuses: any `$`, `%`, or `~` component in a path is an unresolved variable and a typed rejection (crates/superai-config/src/safe_paths.rs:20-26), globs likewise (crates/superai-config/src/safe_paths.rs:15-18), and broad roots such as `/etc` or a bare drive are refused outright (crates/superai-config/src/safe_paths.rs:28-46, with the Windows shapes at crates/superai-config/src/transaction.rs:246-287 and reserved device names at crates/superai-config/src/transaction.rs:291-315).

For a tool that writes into other programs' config directories, refusal is the safer rule. Interpolating `$HOME` from the environment moves an attacker-controllable variable into path resolution, and toride's expander has two quiet failure modes superai's refusal avoids: `~someuser` is returned unresolved and flows downstream as a literal directory name (toride-fs/src/expand.rs:40-43), and an unresolvable home falls back to `.` (toride-fs/src/expand.rs:84-86), producing a relative path where superai's `home_dir` returns None and callers refuse (crates/superai-config/src/safe_paths.rs:3-13, with the refusal on use at crates/superai-config/src/quarantine.rs:12-22).

Verdict: KEEP.

### Backup and catalog

superai's backup.rs takes a digest-verified sibling copy beside the file before a mutation, records mode and size in a catalog entry, and restores through the atomic-write discipline with identity checks so a backup of one file can never restore over another (crates/superai-config/src/backup.rs:120-136 for the exclusive create, crates/superai-config/src/backup.rs:404-418 for restore, crates/superai-config/src/backup.rs:522-552 for the relation gate, crates/superai-config/src/backup.rs:668-742 for the verified restore with a redacted diff preview). toride-backup is a different animal: a restic and borg client that shells out to those binaries, dispatching `restic restore` or `borg extract` through a command runner (crates/toride-backup/src/lib.rs:1-7, crates/toride-backup/src/restore.rs:13-19, restore options at crates/toride-backup/src/restore.rs:42-56), plus a scheduler that installs systemd timer units and cron entries under /etc (crates/toride-backup/src/schedule.rs:1-3).

None of that maps onto superai's need. superai wants an inline, synchronous, no-external-binary copy made milliseconds before a config edit, sized for single files, with no root and no daemon. toride-backup assumes repositories, snapshot ids, and host-level scheduling. Even its best detail, carrying passphrases in environment variables with redaction (crates/toride-backup/src/restore.rs:22-26), answers a problem superai does not have.

Verdict: KEEP. toride-backup is not relevant to config-file backup, by shape rather than by quality.

### Components with no toride counterpart

journal.rs writes a phase-tracked crash journal containing paths and backup ids but never contents (crates/superai-config/src/journal.rs:64-85) and recovers at startup by sweeping only its own temp pattern, restoring from recorded backups, and quarantining corrupt journals aside rather than aborting the scan (crates/superai-config/src/journal.rs:179-199, temp sweep at crates/superai-config/src/journal.rs:322-368). snapshot.rs builds conflict tokens from digest, size, and symlink target, deliberately ignoring hint fields for decisions (crates/superai-config/src/snapshot.rs:51-80, comparison at crates/superai-config/src/snapshot.rs:192-209), plus a capped symlink-loop walk (crates/superai-config/src/snapshot.rs:213-265). transaction.rs validates removal targets against traversal, globs, and broad roots (crates/superai-config/src/transaction.rs:123-177), stages temps before commit (crates/superai-config/src/transaction.rs:426-496), handles cross-device renames with a copy fallback (crates/superai-config/src/transaction.rs:551-559), refuses case-fold collisions (crates/superai-config/src/transaction.rs:592-612), backs up foreign files before the first commit (crates/superai-config/src/transaction.rs:1532-1590), and journals each step as about-to-commit before mutating (crates/superai-config/src/transaction.rs:1688-1699). quarantine.rs moves deletion targets into an owner-only 0o700 directory, verifies digests, and restores across filesystems (crates/superai-config/src/quarantine.rs:289-299, crates/superai-config/src/quarantine.rs:336-360, crates/superai-config/src/quarantine.rs:471-520).

toride-fs has nothing in any of these areas, so there is nothing to adopt or port. The read helpers (toride-fs/src/read.rs:21-36 and toride-fs/src/read.rs:44-59) are NotFound-to-None wrappers; superai's reads go through its own typed error path and gain nothing from them.

### Security notes

The security-relevant findings from this comparison: toride's post-rename chmod-by-path with delete-on-failure (toride-fs/src/atomic.rs:133-137) is both a TOCTOU exposure and a data-loss path. toride's lock file open creates missing files and follows symlinks (toride-fs/src/lock.rs:34-39). toride's env interpolation moves environment control into path resolution (toride-fs/src/expand.rs:68-71). On superai's side, the one gap this comparison surfaced is the missing world-readable audit on secret-bearing configs, covered under permission audits above.

## Process execution

This section reads crates/superai-core/src/process.rs in full against crates/toride-runner/src: runner.rs, spec.rs, policy.rs, duct_runner.rs, discovery.rs, fake.rs, redact.rs, output.rs, and output_mode.rs. The async files (async_runner.rs, tokio_runner.rs, streaming.rs) sit behind non-default tokio features and are weighed under adoption readiness. Publish status checked 2026-10-08: https://crates.io/api/v1/crates/toride-runner returns 200 with max_version 0.1.0, created 2026-10-08, 26 downloads. The four semantics conflicts the 2026-10-01 gap plan recorded (toride-apps-gap-plan.md:115) are now per-spec policy knobs in policy.rs, so those blockers are gone. What still argues against adoption is below.

### Env composition

superai composes one BTreeMap: inherited, or empty under clear_env, then the env additions, then env_remove, which wins on a same key (crates/superai-core/src/process.rs:218-235). That map is duct's only env input (crates/superai-core/src/process.rs:362-366), so precedence never depends on the order duct applies env wrappers. Windows keys fold ASCII-case-insensitively through one canonical key function (crates/superai-core/src/process.rs:204-216). The remove-wins rule is pinned on the composed map (crates/superai-core/src/process.rs:774-793) and end to end through a real child (crates/superai-core/src/process.rs:796-823).

toride's default is the opposite precedence: an explicit env entry beats env_remove (crates/toride-runner/src/duct_runner.rs:601-616, pinned at crates/toride-runner/src/duct_runner.rs:753-762). The conflict is now a knob: EnvPrecedence::RemoveWins (crates/toride-runner/src/policy.rs:17-25) applies removals after additions and is pinned both plain and under clear_env (crates/toride-runner/src/duct_runner.rs:617-625, tests at crates/toride-runner/src/duct_runner.rs:1194-1223). Two differences have no knob. toride's clear_env keeps SystemRoot, SystemDrive, and WINDIR on Windows (crates/toride-runner/src/policy.rs:237-248, applied at crates/toride-runner/src/duct_runner.rs:595-599), which is friendlier to children that need winsock; superai's clear_env is a truly empty map (crates/superai-core/src/process.rs:221-227). And toride's non-clear path is assembled from duct env()/env_remove() wrapper calls (crates/toride-runner/src/duct_runner.rs:601-625), leaning on duct's application order where superai hands over a finished map.

Verdict: KEEP.

### PATH resolution

superai refuses any `.` or `..` component in the executable (crates/superai-core/src/process.rs:293-303), passes absolute and separator-containing programs through, and resolves bare names against the child's composed PATH with the ambient one as fallback, skipping empty entries (POSIX reads them as the cwd), demanding the execute bit, and never searching the working directory (crates/superai-core/src/process.rs:237-289 and crates/superai-core/src/process.rs:291-321). Pinned from three angles: first-match order follows the child PATH (crates/superai-core/src/process.rs:852-873), the cwd is never searched even with a probe sitting in it and a colon-only PATH (crates/superai-core/src/process.rs:875-898), and dot-relative spellings are refused (crates/superai-core/src/process.rs:900-911).

toride's default, PathResolution::OsSearch, passes the program to the OS verbatim, with a which-based PATHEXT lookup for bare names on Windows (crates/toride-runner/src/policy.rs:100-107 and crates/toride-runner/src/policy.rs:134-140). The opt-in ChildEnvNoCwd is superai's algorithm rebuilt: same dot/dotdot refusal, same child-PATH resolution with parent fallback, same empty-entry skip and execute-bit demand (crates/toride-runner/src/policy.rs:109-131 and crates/toride-runner/src/policy.rs:142-212). So the 2026-10-01 conflict is expressible, per spec, off by default. discovery.rs is not in the spawn path at all: binary_exists and find_binary are which-based parent-PATH helpers for pre-flight checks (crates/toride-runner/src/discovery.rs:22-46), while the runner resolves through the policy gate (crates/toride-runner/src/duct_runner.rs:150).

Verdict: KEEP. Under toride, superai's guarantees become per-call-site opt-ins.

### Output limiting

This is the real gap, and it goes the other way. superai's cap is always on, 1 MiB by default (crates/superai-core/src/process.rs:29 and crates/superai-core/src/process.rs:116), but duct's capture buffers the whole stream and the check runs after the child exits (crates/superai-core/src/process.rs:368 and crates/superai-core/src/process.rs:423-435). The cap is a refusal, not a bound: a child that floods stdout until its timeout budget expires is fully buffered in superai's memory before the refusal lands. The DoS exposure is bounded only by the timeout and the producer's rate.

toride, when a limit is in effect, caps while capturing. It wires os_pipe pipes instead of duct capture (crates/toride-runner/src/duct_runner.rs:282-293), runs two reader threads doing 8 KiB bounded reads against a shared atomic counter, and the thread that pushes the total past the cap kills the child immediately (crates/toride-runner/src/duct_runner.rs:19-20 and crates/toride-runner/src/duct_runner.rs:499-549), with a late-breach re-check so a breach noticed after a clean exit still errors (crates/toride-runner/src/duct_runner.rs:429-438). Retained memory stays at cap plus two read buffers (crates/toride-runner/src/duct_runner.rs:499-506). It is tested against a newline-free flood, proving the cap fires rather than the timeout (crates/toride-runner/src/duct_runner.rs:1081-1100), and that the flood actually dies (crates/toride-runner/src/duct_runner.rs:1102-1132). But the path only runs when a limit applies, and the default is OptIn with no limit (crates/toride-runner/src/policy.rs:52-61, defaults at crates/toride-runner/src/spec.rs:107-112), so toride's default capture is unbounded with no refusal either.

Verdict: PORT the in-capture limiting into process.rs. Bounded memory under a flooding child is the one property here superai does not have, and the mechanics (os_pipe, reader threads, counter, latch, kill) are self-contained.

### Redaction

superai redacts argv positions and equals-forms (crates/superai-core/src/process.rs:124-157, flag list at crates/superai-core/src/process.rs:41-55) and scrubs stderr by blanking the entire field to [REDACTED] when any flag keyword appears, only when redact is set (crates/superai-core/src/process.rs:176-188). stdout is never scrubbed (crates/superai-core/src/process.rs:437-442).

toride collects the secret values themselves: values after sensitive flags, the value half of --flag=value, env values whose key matches REDACT_ENV_KEYS (TOKEN, SECRET, PASSWORD, AUTH, GH_, and more, crates/toride-runner/src/display.rs:16-33), and secret assignments in piped stdin. Each occurrence is replaced anywhere in the stream, longest first, with a minimum-length guard against mangling (crates/toride-runner/src/display.rs:264-302). Both streams get this on success when redact is set (crates/toride-runner/src/display.rs:241-250, applied at crates/toride-runner/src/duct_runner.rs:240-243), and the error path adds an always-on 4 KiB stderr byte cap on a char boundary (crates/toride-runner/src/display.rs:177-180 and crates/toride-runner/src/display.rs:406-420). The flag list is a superset of superai's, adding the ssh-keygen -N and -P passphrase flags (crates/toride-runner/src/redact.rs:24-41).

superai needs part of this. The whole-field [REDACTED] scrub is safe but destroys the diagnostic: when a harness fails with a token in the message, superai users lose the entire error text, while toride's users keep everything except the token. A sweep of the places superai composes child env found non-secret values throughout: installs and probes run under clear_env against a fixed non-secret allowlist (crates/superai-core/src/install_execute.rs:43), package probes pass HOME alone (crates/superai-core/src/detect.rs:1205-1215), the activation wrapper launcher passes the wrapper plan's relocation vars (crates/superai-core/src/activation.rs:161, taken from the plan at crates/superai-core/src/activation.rs:115), daemon env is built only inside mod tests (crates/superai-core/src/daemon.rs:960, config literals also at 1297, 1316, 1576, 1647, and 1659), and the git-name additions live under mod tests (crates/superai-core/src/skills.rs:4547-4555, inside the module at crates/superai-core/src/skills.rs:3438). The one secret-bearing env surface is the alias launch composition's secret_env (crates/superai-core/src/alias.rs:1148, filled at crates/superai-core/src/alias.rs:1184), which no code path executes a child with yet, so env-value scrubbing is cheap insurance now and directly useful the day something executes it. stdin secret collection answers a flow superai does not have.

Verdict: PORT the value-level scrub for both streams; skip the stdin half.

### The execution seam

toride's Runner trait is one method plus a checked default (crates/toride-runner/src/runner.rs:15-35). FakeRunner backs it with FIFO or exact-match responses, strict mode, call recording, and shared-state clones so a test can inspect calls after handing the runner away (crates/toride-runner/src/fake.rs:71-135, crates/toride-runner/src/fake.rs:198-212, crates/toride-runner/src/fake.rs:221-252). Its matching ignores runtime policy fields such as timeout and output_limit, so tightening a safety knob does not break every registered fake (crates/toride-runner/src/fake.rs:263-276).

superai has no seam at this layer. run_command is a free function (crates/superai-core/src/process.rs:325) called directly by ten modules (crates/superai-core/src/detect.rs:775-879 among them), and the process tests execute real binaries: /bin/sh, echo, sleep, printenv (crates/superai-core/src/process.rs:626-925). The need has already surfaced once. The update flow grew its own private UpdateCommandRunner trait wrapping run_command so hermetic tests could avoid a real npm (crates/superai-core/src/install_execute.rs:1093-1117). One caller inventing a local trait is the tell that the layer wants one.

Verdict: PORT the design, not the crate. A small trait over (executable, args, ExecuteOpts) returning ProcessOutput in superai-core, run_command behind the real impl, a recording fake beside it, and UpdateCommandRunner folded in. The matching-ignores-policy-fields ruling is the detail worth copying exactly.

### Adoption readiness

Both gates from the routing rules pass: the semantics knobs exist and are tested, and the crate is published. Three things still argue against ADOPT today. First, posture is per-spec. DuctRunnerOptions carries only a default timeout and a log flag (crates/toride-runner/src/duct_runner.rs:30-47), so RemoveWins, ChildEnvNoCwd, an always-on cap, metachar rejection, and stdin_null must be spelled on every CommandSpec, and one forgotten knob silently reverts to toride's looser defaults; stdin inherits the parent terminal unless stdin_null is set (crates/toride-runner/src/spec.rs:33-44), which is wrong for a future GPUI app, while superai pins null stdin unconditionally (crates/superai-core/src/process.rs:368). Second, the publish is one day old, a single 0.1.0 with 26 downloads; the dependency rule asks for evidence of maintenance and there is none yet. Third, the crate drags tracing and which into superai-core (crates/toride-runner/Cargo.toml:22-24), which carries neither today. The async side is irrelevant rather than blocking: AsyncRunner, TokioRunner, and streaming sit behind tokio-runner and stream, which default features never pull (crates/toride-runner/Cargo.toml:13-19; crates/toride-runner/src/lib.rs:64-71), and GPUI runs its own executor, so superai would never enable them. Revisit once the crate shows a release history or grows runner-level policy defaults; the swap itself would be mechanical.

### Security notes

The superai-side finding: the always-on cap buffers a flooding child's full output in memory before refusing (crates/superai-core/src/process.rs:368 and crates/superai-core/src/process.rs:423-435), so a hostile or broken harness can grow superai's RSS to its timeout budget's worth of pipe output. The port under output limiting closes it. On argv injection, superai validates metachars at the config layer, not in the runner (crates/superai-core/src/plugin.rs:45 and crates/superai-core/src/plugin.rs:108, crates/superai-core/src/mcp.rs:59 through crates/superai-core/src/mcp.rs:120, crates/superai-core/src/skills.rs:378, crates/superai-core/src/skills.rs:1174, crates/superai-core/src/skills.rs:2631), and run_command itself checks only NUL (crates/superai-core/src/process.rs:336-349); toride's runner-side ArgvPolicy defaults to Allow (crates/toride-runner/src/policy.rs:41-50), so adoption would move that guarantee to per-spec discipline too. On PATH hijack, both sides skip empty entries and refuse cwd-relative programs in their safe modes; toride's default OsSearch inherits whatever the OS does with a colon-only PATH. On secret leakage, superai's env additions reach the child unscrubbed and its stdout is returned raw. A sweep of child-env composition turned up allowlist vars and HOME (crates/superai-core/src/install_execute.rs:43, crates/superai-core/src/detect.rs:1205-1215), plan relocation vars (crates/superai-core/src/activation.rs:161), daemon env built only inside mod tests (crates/superai-core/src/daemon.rs:960), and git names confined to mod tests (crates/superai-core/src/skills.rs:4547-4555, inside the module at crates/superai-core/src/skills.rs:3438); nothing secret reaches a child env today, which keeps this a hardening item rather than a hole. The alias launch surface's secret_env (crates/superai-core/src/alias.rs:1148) is the future case to watch once something executes it. On toride's side, the default timeout path kills and then calls handle.wait() with no bound (crates/toride-runner/src/duct_runner.rs:189-202), so a descendant holding the capture pipes can stretch a "timed out" call past its budget; superai bounds exactly this with a 500 ms reap grace and an abandonment note (crates/superai-core/src/process.rs:37 and crates/superai-core/src/process.rs:381-414).

### Planning and availability

superai's planner is pure over its inputs: plan_install_for_entry_with_probe takes a request, a catalog entry, a platform pair, and an injected probe, and touches nothing else (crates/superai-core/src/install_plan.rs:422-522). The probe is the interesting half. VersionProbe is a trait (crates/superai-core/src/install_plan.rs:110-119); the real implementation runs `npm view`, `brew info --json=v2`, `cargo search`, `mise ls-remote`, and `pip index versions` per method under a 10 s timeout and a 256 KiB cap (crates/superai-core/src/install_plan.rs:126-257, argv from crates/superai-core/src/install_execute.rs:374-416), and every failure lands in a typed Unavailable carrying the reason; availability is never silently true (crates/superai-core/src/install_plan.rs:73-94). pipe_match_requested then reconciles the registry's answer against the requested version and downgrades to a typed refusal when they diverge (crates/superai-core/src/install_plan.rs:269-294). Around this the planner validates platform constraints from the catalog (crates/superai-core/src/install_plan.rs:429-437), takes package identity only from the catalog (crates/superai-core/src/install_plan.rs:439-457), rejects shell metacharacters and path traversal in versions and channels (crates/superai-core/src/install_plan.rs:524-565), checks destination writability with a create-new probe on Windows (crates/superai-core/src/install_plan.rs:567-646), and derives where the executable should land per method (crates/superai-core/src/install_plan.rs:648-676).

toride's planner is also pure and deliberately dumber: plan_install checks the app's availability flag and platform claims, then routes the method to an Operation with a canonical argv, a dry-run slot, and an explicit requires_elevation verdict for distro managers (crates/toride-apps/src/plan.rs:964-985, routing at 1064-1117). No probe runs at plan time; availability lives in the backends (available_version and available_versions, crates/toride-apps/src/backend.rs:432-453) and the facade consults it before planning (crates/toride-apps/src/apps.rs:770). A requested version is spelled into the method's native addressing and refused when it cannot be spelled: a brew token already carrying a versioned track, a version containing brew's own separator, an empty version (crates/toride-apps/src/plan.rs:1145-1165, 1216-1222).

One superai bug falls out of this comparison. build_command_preview constructs a single versioned operand, `package@version`, and hands it to every method (crates/superai-core/src/install_plan.rs:687-694, arms at 706-743). npm, brew, and mise address versions that way. cargo does not; its native spelling is `--version <v>` (crates/toride-apps/src/plan.rs:76-87). uv uses `package==version` (crates/toride-apps/src/plan.rs:89-94). pipx takes no version operand at all in toride's model (crates/toride-apps/src/plan.rs:415-419). A requested version through superai's cargo, pipx, or uv method therefore renders an operand the manager will not resolve; the bug is latent because those installs run version-less today.

Verdict: KEEP the typed availability and reconciliation, PORT toride's planner shape. The Operation enum with per-method canonical argv, the per-manager verb table (crates/toride-apps/src/plan.rs:216-274), and the elevation and dry-run slots on the plan itself are the cleaner split, and each backend owning its own probe beats superai's install_plan reaching into install_execute for availability_argv.

### Execution, elevation, and suppression

superai executes a plan's tokens through structured_opts: cleared environment with a fixed non-secret allowlist (crates/superai-core/src/install_execute.rs:43-92), a 120 s timeout, a 1 MiB output cap, NUL checks on program and args, and optional redaction (crates/superai-core/src/install_execute.rs:109-153). No shell is ever invoked. After the command succeeds, verification is a refusal chain: re-detect through the same detector, treat the same canonical path as the same installation rather than a new one (crates/superai-core/src/install_execute.rs:581-597), confirm the detected version satisfies the request with semver requirements where parseable (crates/superai-core/src/install_execute.rs:425-464), run a smoke probe of --help/--version/-h/help (crates/superai-core/src/install_execute.rs:466-520), and only then write a receipt (crates/superai-core/src/install_execute.rs:681-690). A verify step that fails is an error, not a warning.

toride's backends dispatch the plan's canonical argv through one CommandRunner seam, with stdin_null forced on every command (crates/toride-apps/src/runner.rs:49-59, 143-156). Two contracts run before anything mutates: dry-run plans are refused, and a plan that requires elevation without an explicit grant is refused; backends never construct sudo themselves (crates/toride-apps/src/backend.rs:632-699). Suppression flags are layered at execution per manager and never pollute the canonical argv: apt gets -y plus DEBIAN_FRONTEND=noninteractive, dnf gets -y, pacman gets --noconfirm because its -y is a database-sync flag, apk gets nothing because it has no -y (crates/toride-apps/src/backends/distro.rs:14-27 and 298-309, applied at 694-725). Post-install verification is kind-aware presence and version probing, and a probe that cannot confirm degrades to a warning on the outcome while the record is written unverified (crates/toride-apps/src/apps.rs:777-799).

The differences that matter for superai. superai has no elevation concept because none of its seven executable methods needs root; requires_admin is catalog data surfaced in plans (crates/superai-core/src/install_catalog.rs:295-297), and nothing elevates. toride's typed ElevationRequired refusal is the better answer the day a distro method enters the catalog. In the other direction, toride's execution seam adds only cwd and env additions to a spec (crates/toride-apps/src/runner.rs:113-121); a child otherwise inherits the ambient environment, so anything in superai's process env reaches brew, npm, and cargo. superai's clear-env allowlist is the stronger posture for a tool that may sit in an environment carrying provider tokens.

Verdict: KEEP superai's execution and its verify-or-refuse chain; PORT the elevation and dry-run guard shape and the per-manager suppression table. The warning-and-record-unverified path is a genuine philosophy difference: superai's receipt is a delete license, so it should only exist when verification earned it.

### Method coverage

superai's nine kinds against toride's backends, with where each argv comes from today in superai:

- Mise: `mise use -g <pkg>[@v]` (crates/superai-core/src/install_plan.rs:707-717). toride runs a two-step `mise install <spec>` then `mise use --global`, behind the tokio-carrying mise feature (crates/toride-apps/src/plan.rs:607-615, crates/toride-apps/src/backends/mise.rs:31-37). toride's two-step is the more correct activation; superai's single use -g implicitly installs in current mise versions.
- Homebrew and HomebrewCask: superai emits one shape, `brew install <pkg>[@v]`, for both kinds (crates/superai-core/src/install_plan.rs:718-721); the cask distinction survives only in detection and in derived paths. toride distinguishes `--cask` on install and uninstall and offers zap for casks (crates/toride-apps/src/plan.rs:286-304, 506-524).
- Npm: `npm install -g <pkg>[@v]` on both sides (crates/superai-core/src/install_plan.rs:722-725; crates/toride-apps/src/plan.rs:67-74).
- Cargo: `cargo install <pkg>[@v]` in superai (crates/superai-core/src/install_plan.rs:726-729) versus `cargo install [--version <v>] [--force] <crate>` in toride (crates/toride-apps/src/plan.rs:76-87), with --force as the upgrade verb since cargo has none (crates/toride-apps/src/plan.rs:408-414).
- Pipx: `pipx install <pkg>[@v]` versus `pipx install <package>`, version operand deliberately absent (crates/toride-apps/src/plan.rs:415-419).
- Uv: `uv tool install <pkg>[@v]` versus `uv tool install <package>[==<v>]` (crates/toride-apps/src/plan.rs:89-94).
- Direct: typed refusal on both counts in superai; a real verified pipeline in toride behind the direct feature.
- External: superai types it, plans an `open <docs>` preview, and refuses execution with ExternalInstallRequired carrying the docs URL (crates/superai-core/src/install_plan.rs:485-499 and 696-704; refusal at crates/superai-core/src/install_execute.rs:705-710; error at crates/superai-core/src/error.rs:423-428). toride has no External concept; an unroutable method is UnsupportedMethod at plan time (crates/toride-apps/src/plan.rs:1109-1116). The typed handoff with a URL is domain value superai should keep.
- Distro (apt/dnf/pacman/apk) and flatpak exist only in toride; superai's catalog deliberately has no system-package method kind (crates/superai-core/src/install_catalog.rs:23-42).

Update and uninstall argv in superai come from the catalog's update and uninstall token fields when present, falling back to per-method arms: `npm update -g`, `cargo install`, `uv tool update`, `brew upgrade`-shaped `upgrade <pkg>` for brew, mise, and pipx (crates/superai-core/src/install_execute.rs:974-999); uninstall arms mirror them (crates/superai-core/src/install_execute.rs:1450-1472). toride derives every verb from the planner's Operation variants and replays the recorded identity for uninstall and update, never re-resolving through the registry (crates/toride-apps/src/apps.rs:877-883, 1017).

Verdict: KEEP the nine-kind model and the External handoff; PORT toride's per-method native version spellings (fixing the cargo/pipx/uv operand bug) and the record-replay rule for uninstall and update.

### Detection

superai's detect.rs returns every hit for a harness from nine sources: PATH scan with ranks, a configured-binary override from the registry or SUPERAI_CONFIGURED_BINARY_<HARNESS> (crates/superai-core/src/detect.rs:364-430), mise shims and `mise where`, `brew list --versions`, `npm list -g --json`, `cargo install --list`, pipx and uv listings, dpkg status, and macOS app bundles read from their Info.plist without executing anything (crates/superai-core/src/detect.rs:20-42, probes at 873-1000, 1002-1202, 1264-1352, 1353-1395, 1396-1411). Each hit carries version, source, confidence, PATH rank, and three hazard flags: shadowed, broken_shim (a mise shim without the exec bit or without an installed version, checked at crates/superai-core/src/detect.rs:855-871), and arch_mismatch from `file` output (crates/superai-core/src/detect.rs:826-853), plus evidence lines for diagnostics (crates/superai-core/src/detect.rs:85-112). Probes run concurrently through scoped threads (crates/superai-core/src/detect.rs:253-357), and duplicate paths are deduped by canonical path, first sighting winning (crates/superai-core/src/detect.rs:742-751).

toride's MultiSourceDetector covers ten sources, separating what superai lumps as SystemPackage into Pipx, Uv, and Distro(family), and adding Flatpak (crates/toride-apps/src/detect.rs:25-46). Its merge is better: hits grounding at one canonical path are absorbed rather than dropped, upgrading a PATH hit to the managed source that also reports it, joining ranks, ORing the hazard flags, and maxing confidence (crates/toride-apps/src/detect.rs:191-225). Its arch probe uses `file -b` and compares against the target's arch enum (crates/toride-apps/src/detect.rs:310-320). What it lacks for superai's domain: no configured-binary override, no app-bundle probe, no dpkg, and mise-shim brokenness is only detectable when the mise feature's backend is attached (crates/toride-apps/src/detect.rs:339-357). And it is a standalone seam: the facade's status is still manifest-first with backend probes, not this detector (crates/toride-apps/src/apps.rs:1348), so adopting toride-apps would not retire detect.rs anyway.

Running both would produce two vocabularies for the same facts (superai's SystemPackage evidence names its manager; toride's sources are per-backend), and superai's install-skip, foreign, and pin decisions read its own Detection model directly (crates/superai-core/src/install_execute.rs:522-543, 1080-1091). One detector must own those decisions.

Verdict: KEEP detect.rs. PORT the absorb-merge semantics into push_unique so a PATH hit that a package listing also reports carries both signals instead of whichever ran first.

### Ownership and receipts

superai's ledger is receipts under ~/.superai/install_receipts/<harness>-<method>.json, written only when verification proved a new install: pre-existing binaries are never claimed, with the same canonical path reading as the same installation (crates/superai-core/src/install_execute.rs:178-192, 236-238, 551-597; persistence through superai-config's transactional commit at 246-272). Loading fails closed on any unparseable receipt (crates/superai-core/src/install_execute.rs:276-310). Uninstall consults the receipt before anything else: a managed source or a receipt permits auto-delete, everything else is foreign and refused with ForeignOwnership unless the caller explicitly allows (crates/superai-core/src/install_execute.rs:1425-1447, 1524-1537), the plan rejects an rm preview outright, and no argument may name a preserved path, a list that includes the receipts directory itself (crates/superai-core/src/install_execute.rs:1336-1370, 1541-1563).

toride's ledger is one manifest record per app, keyed by TorideId, carrying backend-native identity (NativeIds with variants for every backend including Direct provenance, crates/toride-apps/src/manifest.rs:150-215), saved atomically (temp plus rename, crates/toride-apps/src/manifest.rs:495-520). Unrecorded presence is Foreign and removal is refused without force (crates/toride-apps/src/apps.rs:932-937); a detected install can be claimed with adopt, which probes once and records without running any mutating command (crates/toride-apps/src/apps.rs:1068-1098); a corrupt document is quarantined to a .corrupt sibling and the store starts empty rather than failing (crates/toride-apps/src/store.rs:91-129). The RecordStore trait is the seam that makes this embeddable: superai could back the facade with its own receipts, and the module docs say exactly that (crates/toride-apps/src/store.rs:3-9).

Two properties keep superai's model the safer one for its own posture. Freshness: toride loads records once at build and keeps them in memory for the facade's lifetime, while superai rereads receipts from disk per operation; a long-lived facade can act on a record another process already removed. Failure direction: toride's quarantine turns an unreadable ledger into an empty one, so previously-owned installs stop being proven owned (the refusal direction stays safe, but the proof is gone), where superai's fail-closed parse refuses to proceed at all. The one thing toride has that superai lacks is adopt, and it is the right shape: bookkeeping over a detection, zero commands.

Verdict: KEEP receipts and the ForeignOwnership gates; PORT adopt as a receipt-writing claim over superai's own detections.

### Direct downloads

superai's direct method is an honest refusal: plans carry external_install with the reason that no verified installer adapter exists (crates/superai-core/src/install_plan.rs:492-497), execution and update both refuse typed (crates/superai-core/src/install_execute.rs:705-710, 1155-1166), and the catalog's checksum field is validated for shape only, 64-hex sha256 or an https URL, with the field's own comment noting no download path exists yet (crates/superai-core/src/install_catalog.rs:298-301 and 357-368).

toride-installer is the complete pipeline superai would otherwise have to write: resolve, download capped on the stream with a content-length precheck, per-chunk abort, and a stall timeout (crates/toride-installer/src/installer.rs:361-462), digest from the tool config or fetched from a checksum URL (crates/toride-installer/src/installer.rs:477-495), verification where Strict refuses a missing checksum outright and a known digest pins the bytes as sha256 or sha512 by hex length, compared case-insensitively (crates/toride-installer/src/installer.rs:707-756), extraction, and an atomic install write whose temp is created 0o755 from the start, fsynced, then renamed (crates/toride-installer/src/installer.rs:648-689).

On zip-slip specifically: there is no archive unpack to disk anywhere. extract_tar_entry walks entries in memory and returns one entry's bytes (crates/toride-installer/src/extract.rs:44-117), so no entry path ever reaches the filesystem and there is no path to escape. Symlink handling falls out of the same structure: only entries whose header type is a regular file can match (crates/toride-installer/src/extract.rs:88-90), so a symlink or hardlink named like the binary is skipped, not followed. Two caveats. Matching is on the bare final path component and the first matching regular file in archive order wins (crates/toride-installer/src/extract.rs:59-66 and 88-108); under Strict the whole artifact is digest-pinned so a shadowing entry implies a digest mismatch, but under Lenient, an explicit opt on the backend (crates/toride-apps/src/backends/direct.rs:80-84 strict default, 108 for the opt), a hostile archive chooses which same-named file you run. And the destination write is a rename over whatever is there, so a pre-planted symlink at the destination is replaced rather than written through. The backend layer adds its own confinement: bin_name must be a single path component (crates/toride-apps/src/backends/direct.rs:122-127), and uninstall canonicalizes the target, requires its parent to be the backend's install dir and the target to be a regular file before deleting exactly that (crates/toride-apps/src/backends/direct.rs:161-208).

Verdict: PORT the design into superai when the direct method gains an executor, and reuse these exact defenses. ADOPT the crate only when tokio is acceptable in superai-core: the direct feature drags tokio, reqwest, and xz2 with it (crates/toride-apps/Cargo.toml:21-24), the pipeline is async at its core, and the backend's sync twins spin a per-call current-thread runtime with an explicit warning never to call them from async context (crates/toride-apps/src/backends/direct.rs:17-20). GPUI is not tokio.

### Sync and async

The 2026-10-01 blocker is gone. Default features pull no tokio (crates/toride-apps/Cargo.toml:13-14); every Backend operation has a _sync twin (crates/toride-apps/src/backend.rs:497-521); AppsBlocking drives the lifecycle synchronously with in-line manifest saves (crates/toride-apps/src/apps.rs:2246-2292); and without the tokio feature even the async spellings execute on the calling thread (crates/toride-apps/src/runner.rs:193-203). Two costs remain for an all-sync embedder. AppsBlocking::ensure_installed takes an already-resolved registry App because the adapter trait is async and the blocking surface cannot resolve a bare id itself (crates/toride-apps/src/apps.rs:2281-2292). And the two features superai would most want, mise for its preferred method and direct for its missing one, are precisely the two that carry tokio (crates/toride-apps/Cargo.toml:23-28); npm, cargo, pipx, uv, and brew stay tokio-free.

Verdict: KEEP superai's all-sync stack. The sync surface is real now, so this axis is no longer the blocker it was; it is just not free either.

### Swapping the stack today

Not yet, and the reasons are structural rather than gate-related. The identity layer is the first: toride resolves TorideIds through registry adapters and plans from a network-shaped App model, while superai's identity is a compile-time embedded catalog carrying per-harness methods, platform constraints, conflicts, executables, requires_admin, docs, and a checksum guard (crates/superai-core/src/install_catalog.rs:263-311). A swap means translating each catalog entry into a toride-registry App before every plan and keeping the fields toride has no slot for in a shim beside it. The second is posture: children inherit the ambient environment through toride's seam unless every spec carries env policy, and the process section already established that toride's guarantees are per-spec opt-ins rather than layer defaults. The third is verification philosophy: record-unverified-with-warning against refuse-and-no-receipt. The fourth is history: four crates published today, with download counts in the single digits.

If the swap ever happens, what superai deletes is the argv plumbing: build_command_preview (crates/superai-core/src/install_plan.rs:682-745), the update and uninstall fallback arms (crates/superai-core/src/install_execute.rs:974-999 and 1450-1472), availability_argv (crates/superai-core/src/install_execute.rs:374-416), and the raw run_command arms inside execute_and_verify, execute_update, and execute_uninstall. What it keeps is everything that makes the decisions: the catalog and its validation, detect.rs and discovery.rs, receipts with the ForeignOwnership and preserved-path gates, verify_install with its smoke probe, compatibility gating and post-update revalidation, and instance marking. What toride must still gain, or superai must wrap: a RecordStore implementation over the receipts, runner-seam env policy defaults, an External-style typed handoff, and update target pinning.

### Security notes

On argv injection, both sides execute without a shell, so a poisoned package name is a rejected operand rather than a command. superai additionally validates metacharacters on every token at plan time and again before execution (crates/superai-core/src/install_catalog.rs:75-124; crates/superai-core/src/install_plan.rs:524-565; crates/superai-core/src/install_execute.rs:733, 1167, 1564), while toride constructs argv only from typed operations but passes registry-App fields into it verbatim with no metachar screen (crates/toride-apps/src/plan.rs:504-601); with the http feature those fields arrive from network adapters. On archive handling, toride-installer's in-memory single-entry extraction removes the zip-slip class structurally, with the Lenient opt being the one doorway to keep shut. On symlink races, the temp-plus-rename install write and the canonicalized, parent-confined direct uninstall are both sound. On TOCTOU, superai's find_receipt-then-execute window exists but a forged receipt must still survive validation, and the receipt gates only superai's own delete; toride's build-time-loaded records widen the equivalent window to the facade's lifetime. The new superai-side finding from this section is the version-operand bug under method coverage: three managers receive npm's `@`-syntax where their own differs, latent until a version is requested through those methods.

## Update, upgrade, and migration

This section reads superai's template_update.rs and template_fetch.rs in full, the update flow inside install_execute.rs, the registry schema handling in registry.rs, and the instance surfaces in lifecycle.rs, instance.rs, and wrapper.rs, against toride-apps' update verb (apps.rs, backend.rs, plan.rs, manifest.rs), the toride-updates crate, and toride-mise's tool upgrade path. Publish status checked 2026-10-08: https://crates.io/api/v1/crates/toride-updates returns 200 with max_version 0.1.0, created 2026-10-08T13:33:44Z and 0 downloads, so it is in the published set; it went up a few hours after the four crates the install section checked, which is why that section's list does not name it. toride-mise re-checked the same day: 200, max_version 0.1.0, created 2026-10-08T11:10:44Z, 8 downloads, matching the install section's numbers.

"Update" means three different things across these crates, and the section keeps them apart: superai upgrading a harness binary it manages, superai moving an instance to a newer template, and an OS keeping its own packages current. "Migration" also splits in two: schema migrations of superai's own records, and moving an instance's files between directories or machines.

| superai component | toride counterpart | verdict | reason |
|---|---|---|---|
| harness update flow, plan_update + execute_update | Apps::update + Backend::update | KEEP, PORT the outcome shape | compat gating, explicit accept, and strict post-update verify are superai domain logic; toride's UpToDate and Preview outcomes answer questions ProcessOutput cannot |
| mise update arm | toride-mise upgrade path | KEEP | an async tokio executor behind a builder; superai's arm is one argv; minimum-release-age is the one idea worth copying |
| template updates, template_update.rs | none in toride | KEEP | no counterpart exists anywhere in toride |
| template fetch, template_fetch.rs | none in toride | KEEP | nearest cousin is a download-URL templater, not content fetch |
| OS patch scheduling (not wanted) | toride-updates | KEEP, not relevant | unattended-upgrades and dnf-automatic configuration under /etc is another domain |
| registry schema migration, registry.rs | manifest schema gate | KEEP | superai has a real migrate step plus foreign-key preservation; toride refuses both directions |
| instance move, repair, wrapper regen | none in toride | KEEP | no counterpart exists |

### Harness binary updates

superai's flow is a plan, a gate, an execution, and a proof. plan_update never executes anything (crates/superai-core/src/install_execute.rs:929-941): it detects the current install, probes the available version through the method's own view command under a cleared environment (crates/superai-core/src/install_execute.rs:867-927), and runs update_compat_for_versions (crates/superai-core/src/install_execute.rs:821-865). The compat rule: same major passes, a major bump is breaking until explicitly accepted, and with no current version a target below 1.0 whose minor is at least 1 reads as pre-stable and blocks, while 1.0 and later and 0.0.x pass (crates/superai-core/src/install_execute.rs:830-857); a version that will not parse is treated as incompatible (crates/superai-core/src/install_execute.rs:859-863). The plan lands blocked with a reason naming explicit accept as the way through (crates/superai-core/src/install_execute.rs:1051-1061). execute_update_with_runner then refuses a blocked plan without that acceptance (crates/superai-core/src/install_execute.rs:1145-1152), refuses External and Direct as typed states rather than fake commands (crates/superai-core/src/install_execute.rs:1153-1166), runs the command under the structured opts, and after success re-detects and requires the installed version to satisfy the expected available, refusing on an empty probe, a missing version, or a mismatch (crates/superai-core/src/install_execute.rs:1200-1237). revalidate_instances_after_update then reports per-instance compatibility read-only, touching neither registry nor config (crates/superai-core/src/install_execute.rs:1241-1279).

toride's verb is leaner. Apps::update requires a record, replays the record's own identifiers into an update plan with no registry round trip (crates/toride-apps/src/apps.rs:1012-1017), and refuses a requested target version outright while pinning is unimplemented (crates/toride-apps/src/apps.rs:1005-1011; the option documents the refusal at crates/toride-apps/src/apps.rs:398-399). A dry run previews the argv plus the resolved from and to versions without executing (crates/toride-apps/src/apps.rs:1021-1027); an up-to-date install short-circuits through the manager's own stale signal before anything runs (crates/toride-apps/src/apps.rs:1028-1033); execution goes through Backend::update with an explicit elevation grant (crates/toride-apps/src/apps.rs:1034-1035, trait at crates/toride-apps/src/backend.rs:404), and the record is rewritten in place after a re-probe (crates/toride-apps/src/apps.rs:1036-1043). The blocking twin enforces the same target refusal (crates/toride-apps/src/apps.rs:2515-2522). Every backend has an update operation, brew, flatpak, distro, npm, cargo, pipx, uv, and mise (crates/toride-apps/src/plan.rs:343-360 and 387-469), and the cargo one is honest about its manager: re-install under --force, since cargo has no upgrade verb (crates/toride-apps/src/plan.rs:410).

Two things there are better than superai's equivalents. The outcome enum distinguishes UpToDate, Updated with from and to, and Preview (crates/toride-apps/src/apps.rs:438-468), where superai returns a ProcessOutput and leaves the caller to re-detect what happened. And the up-to-date short-circuit answers before running a command. Two things are worse. The post-update record is saved with whatever the re-probe returned, including no version at all (crates/toride-apps/src/apps.rs:1036-1043), where superai's verify-or-refuse chain at install_execute.rs:1210-1235 treats a failed probe as the error it is. And the elevation grant is per-call discipline rather than a layer default, the same posture split the process section recorded.

On pinning the two are even: toride refuses a target version (crates/toride-apps/src/apps.rs:1005-1011) and superai's update argv addresses the package by name only, with no version operand in any fallback arm (crates/superai-core/src/install_execute.rs:979-997).

Verdict: KEEP the flow, PORT the outcome shape. A three-value result (up to date, updated with versions, previewed) is a small change to plan_update's return that retires the re-detect the caller does today.

### The mise upgrade path

toride-mise wraps the mise CLI as a typed executor. Mise::upgrade is a thin `mise upgrade [tool]` (crates/toride-mise/src/tool/upgrade.rs:150-161); upgrade_with builds the full argv from an UpgradeRequest carrying bump, dry run, exclude lists, parallel job counts, and a minimum-release-age that skips releases younger than the given span (crates/toride-mise/src/tool/upgrade.rs:46-67, applied at 170-209). Outdated checking parses mise's JSON, and the crate is honest about a shape bug it carries: the Vec-returning method documents that real mise emits an object and cannot deserialize into it, and points at outdated_map as the canonical fix (crates/toride-mise/src/tool/upgrade.rs:213-224). Activation is scoped through UseScope, Local, Global, Path, or Env (crates/toride-mise/src/tool/install.rs:17-24), with an optional --pin that freezes the resolved version in config (crates/toride-mise/src/tool/install.rs:374). The install path runs install then `use --global`, the two-step the install section already noted as more correct than superai's single use.

Adopting any of this is blocked the same way the install section found: the client is async over tokio (crates/toride-mise/src/client.rs:122, with the tokio-runner and stream features pulled at crates/toride-mise/Cargo.toml:24), and superai-core is all-sync. superai's own mise arm needs none of the surface; it emits one upgrade argv through the shared runner. The single idea worth porting is minimum_release_age as supply-chain cooling, a one-flag addition the day superai grows mise invocation options. Verdict: KEEP.

### Template updates

This whole subsystem is superai's alone. preview_three_way computes a three-way merge over each owned selector: local equal to base takes the new value, new equal to base keeps the local override, both differing is a typed conflict, and foreign keys are never touched (crates/superai-core/src/template_update.rs:406-604, conflict kinds at 195-208). A major version bump cannot silently drop selectors: any selector the new template drops becomes a SelectorReset conflict requiring explicit resolution, while a minor bump auto-removes it (crates/superai-core/src/template_update.rs:442-450 and 542-554). Yanked and deprecated candidates warn, the deprecated warning naming the replacement when one exists (crates/superai-core/src/template_update.rs:421-439), and migration notes surface in the preview with secret-like values redacted (crates/superai-core/src/template_update.rs:451-462).

apply_update_with_catalog_digests is the disciplined half. Both byte sets are verified in memory against id, version, size cap, and the catalog digests before anything happens (crates/superai-core/src/template_update.rs:623-682, called at 728-729); the candidate is validated against the receiving adapter so selector ownership and capability coverage hold before mutation (crates/superai-core/src/template_update.rs:743); the instance is re-read fresh from the registry and the config snapshot is rechecked so an external edit between read and apply aborts (crates/superai-core/src/template_update.rs:745-786); the apply is a transaction whose failure path rolls back and quarantines residuals (crates/superai-core/src/template_update.rs:877-937); the wrapper is regenerated when the template changes its env or args (crates/superai-core/src/template_update.rs:831-865); and the registry record moves to the new version only after all of that, written last (crates/superai-core/src/template_update.rs:979-1019).

toride has no counterpart, and the check was exhaustive over the workspace rather than over the app crates alone: the word template appears in toride only as release-URL templates in toride-installer (crates/toride-installer/src/tool.rs:6 and crates/toride-installer/src/installer.rs:588-599), TUI recipe screens in the desktop crate, and fail2ban and ufw config templating. Nothing is versioned per instance, nothing merges three-way, nothing applies content into a foreign program's config. The registry adapters fetch metadata about apps, not artifacts applied to user files. Verdict: KEEP. There is nothing to adopt, nothing to port, and the fetch discipline below is what any future toride-side equivalent would have to grow first.

The fetch side deserves its own verdict because it is where the risk lives. template_fetch allows only https (and file URLs for tests), rejects control characters and traversal, and refuses private and loopback hosts including the IPv6-mapped and decimal spellings (crates/superai-core/src/template_fetch.rs:151-216). Redirects are followed manually with ureq's own following disabled, so every hop re-passes the full validation, and a redirect to a private host or a non-https scheme dies at the hop (crates/superai-core/src/template_fetch.rs:303-333, agent config at 387-398). The body is bounded twice, a content-length precheck and a capped reader (crates/superai-core/src/template_fetch.rs:353-378), and the fetched bytes must match the catalog entry's sha256 before they are parsed or returned (crates/superai-core/src/template_fetch.rs:519-533). Verdict: KEEP. One honest limitation below under security notes: the catalog itself has no second anchor.

### OS-package update scheduling

toride-updates configures the operating system's own update machinery: unattended-upgrades on Debian-family hosts and dnf-automatic on Fedora (crates/toride-updates/src/lib.rs:1-5). It renders those tools' config files from a declarative UpdateSpec (crates/toride-updates/src/spec.rs:84-99, renderers at crates/toride-updates/src/render.rs:24, 80, and 155), manages systemd timer drop-ins under /etc with a cron fallback (crates/toride-updates/src/schedule.rs:1-4 and 58, drop-in paths at 191-206), applies updates through the system package manager (crates/toride-updates/src/client.rs:105), and diagnoses the result with a doctor that checks service state, schedule presence, last-run freshness, and world-writable config directories (crates/toride-updates/src/doctor.rs:56, the permission check at 293). The spec-to-render-to-validate pipeline is clean, and validate_spec returns severity-tagged findings rather than a boolean (crates/toride-updates/src/validate.rs:24 and 83-126).

None of it maps onto superai. superai updates user-space applications through their own package managers, schedules nothing, runs no root daemons, and writes nothing under /etc. The scheduling and doctor machinery solves host administration problems superai does not have. The one detail with any pull is the finding shape: id plus severity beats the plain warning strings UpdatePreview carries (crates/superai-core/src/template_update.rs:384), and that is a cosmetic change, not a port. Verdict: KEEP, not relevant. Nothing superai owns would be deleted under this axis because there is no overlap to swap.

### Schema migrations

goal.md assigns harness-config migrations across breaking changes to the config layer (docs/goal.md:86), and the migration machinery that exists today lives one layer up, in core's registry. Registry::load reads the file fresh, refuses an explicit schema_version it does not know (crates/superai-core/src/registry.rs:434-453), and transparently upgrades two legacy shapes, a bare array and an unversioned object, trying the current Instance shape first and falling back to OldInstance through migrate_old_instance, which revalidates every field and marks the result AdoptedLegacy rather than pretending it was always current (crates/superai-core/src/registry.rs:322-381, branches at 470-533). The registry owns exactly two keys, schema_version and instances, and store preserves every foreign top-level key on write-back (crates/superai-core/src/registry.rs:383-390 and 552-553), the same disk-is-truth discipline the config layer enforces. Template and catalog documents carry their own version constants and refuse a mismatch outright rather than migrating (crates/superai-core/src/template.rs:17 and 20, gates at crates/superai-core/src/template.rs:413-420 and 787-796).

toride's manifest holds the same line with a stricter gate and no migration. The schema version is a private constant (crates/toride-apps/src/manifest.rs:96); load probes the version before trusting the body, so a newer toride's document is rejected as written-by-a-newer-toride and an older one as having no migration (crates/toride-apps/src/manifest.rs:409 and 420-441); unknown fields inside a matching-version document stay tolerated so additive changes remain readable (crates/toride-apps/src/manifest.rs:87-89). The doc comment says the constant, the reader, and an explicit migrate step move together when the schema grows (crates/toride-apps/src/manifest.rs:84-96). No migrate step exists yet; version 1 has never needed one, the same reason superai's registry still refuses an explicit unknown version while upgrading only the unversioned legacy shapes.

The comparison favors superai on substance: it has the migrate step toride has not needed, and its foreign-key preservation is a rule toride's manifest does not carry. The stage-one version probe, the one elegant toride detail, is already superai's behavior too, reading schema_version before parsing instances (crates/superai-core/src/registry.rs:434-469). Verdict: KEEP on both axes, nothing to port.

### Instance migration between machines and directories

toride has no instance concept at all. Its manifest records package installs; nothing in toride-apps or toride-updates copies, relocates, or repairs a configuration directory, because there is nothing per-user to relocate. superai's surfaces here are the lifecycle set: plan_mirror through create_mirrored copy a config root into an isolated instance under adapter exclusions and a credential gate (crates/superai-core/src/lifecycle.rs:2028, 2110, and 2731); rename_instance moves the wrapper file and updates the record in one step (crates/superai-core/src/lifecycle.rs:3156, pinned at 8808); adopt claims an unmanaged root with every check re-proven fresh at commit and the registry record written last (crates/superai-core/src/lifecycle.rs:1149 and 1331-1337); repair detects and heals wrapper drift, template-version drift, and missing binaries (crates/superai-core/src/lifecycle.rs:5071 and 5418, pinned at 8952 and 9006); orphaned wrappers and unmanaged roots get resolution and quarantine paths rather than deletion (crates/superai-core/src/lifecycle.rs:5644 and 5814). Wrappers themselves are generated deterministically with secrets never embedded, recognized as owned by digest, and removed only under that digest check (crates/superai-core/src/wrapper.rs:1-2, 87, 369, and 407), and the instance record carries the adapter revision it was built against so drift is detectable at all (crates/superai-core/src/instance.rs:68). Verdict: KEEP; no counterpart exists.

### Security notes

The template fetch chain has one trust root: the catalog. Template bytes are digest-pinned against catalog entries before parse (crates/superai-core/src/template_fetch.rs:519-533), redirects cannot leave https or reach private hosts (crates/superai-core/src/template_fetch.rs:303-333), and the fetch-to-apply TOCTOU is closed by re-verifying the same bytes against the same digests in memory at apply time (crates/superai-core/src/template_update.rs:728-729). But the catalog itself is fetched over TLS with no signature or second anchor (crates/superai-core/src/template_fetch.rs:447-461), so a compromised catalog host swaps the file and its digest together. No archives are ever unpacked; templates are single JSON documents, so the zip-slip class does not exist on this path. The new superai-side finding from this section is on the harness update flow: both the compat block and the post-update verification depend on the availability probe, and when that probe fails the plan is not blocked, because blocked requires a known available version (crates/superai-core/src/install_execute.rs:1051-1053), and the post-update check is skipped for the same reason (crates/superai-core/src/install_execute.rs:1203-1204). An update whose version cannot be probed therefore runs ungated and unverified in one pass. On the toride side, toride-updates assumes root and writes under /etc by design (crates/toride-updates/src/schedule.rs:191-206), which is precisely why none of it belongs in superai, and toride-mise pushes caller-supplied tool specs into argv verbatim with no metachar screen (crates/toride-mise/src/tool/upgrade.rs:200-207), the same per-spec posture split the process section recorded for the runner.
